# ADR-001: Policy Engine — dos call sites, un componente

**Estado:** Aceptado
**Fecha:** 2026-09-10

## Contexto

El diagrama de capas del daemon (docs/ARG0S.md sección 4.1) muestra el Policy
Engine como un único gate entre el Context Compiler y el Execution Engine.
Pero el flujo del Router (sección 8, paso 3) describe un "policy check" que
ocurre antes de elegir tier y modelo, dentro del propio router. Esto genera
la pregunta: ¿son dos policy engines, o el mismo evaluado dos veces con
distinto alcance?

## Decisión

Es el mismo componente, con dos métodos de responsabilidad distinta:

- **`Filter(profile) → set de providers/modelos permitidos`**
  Lo llama el Router, antes de elegir tier. Reduce candidatos según reglas
  de policy (ej: `secret_paths_never_cloud` excluye providers cloud). No
  bloquea nada — solo filtra el espacio de búsqueda antes de que el router
  decida.

- **`Authorize(req) → decisión final`**
  Lo llama el Executor, con el modelo ya elegido y el costo estimado. Es el
  único punto que puede denegar la ejecución o pedir confirmación humana
  (P9). El diagrama de capas muestra solo este gate porque es el que
  efectivamente corta la ejecución.

## Consecuencias

- `internal/policy/policy.go` expone ambos métodos en su interfaz pública.
- El Router (Fase 2) consume `Filter`; el Executor (Fase 1, con Policy
  Engine básico desde Fase 2) consume `Authorize`.
- No se crea un segundo paquete ni una segunda implementación — un solo
  Policy Engine, dos entradas.
